# The cache holds raw scan output and the response renders per request

The scan cache used to store one rendered `FlaggedView` per `ViewMode`: a slot for gaps and a slot for show-all. That split started life as two walks, then survived after ADR-0012 unified the walks because each mode kept a different rendered tree. With the gaps and show-all trees now provably equivalent up to a `reduce_to_flagged` filter (Task 3 of this rework, plus the parity tests `unified_build_emits_a_show_all_forest_for_every_input_folder` and `unified_build_matches_today_build_for_a_gaps_input` in `src/tree.rs::tests`), the second cache slot did not earn its complexity: four mode-aware cache methods, two edit closures per marker write, dual section rebuilds on undo, doubled memory once both slots warmed, and a full walk on the first mode flip.

The cache now holds one `Option<CacheEntry>` of `Arc<RawView>`. A `RawView` is one `RawRootSection { path, state }` per configured root, and `RawRootState` is `Clean | Walked(Vec<ScannedFolder>) | Error(String)`. A request takes the lock, gets or builds the raw view, drops the lock, and renders per `ViewMode` (filter for gaps, then build the tree). The rendered `FlaggedView` is constructed per response and dropped after the response writes.

The trade-off is per-request render cost in exchange for mode-flip latency, cache memory, write-path simplicity, and a smaller cache API. Render cost was measured before this rework landed (scan_bench schema v4 plus the new `tree_bench` example, see `docs/superpowers/specs/2026-06-19-unified-scan-cache-design.md`). On the `mixed-forest` reference scenario (81 directories across three roots) the worst per-mode render across all roots and modes measured 0.086 ms, well under the 2 ms gate. On the synthetic 10k-folder shape sweep the worst (depth, fanout) row measured 3.758 ms for gaps and 8.558 ms for show-all, well under the 25 ms gate. Both numbers come from the Decision Gate run that preceded this commit.

Two cost shapes worth calling out so the trade is honest. First, the render runs on every read, not just on a cache miss, so total CPU per TTL window scales with request count. A session that swaps sections a dozen times in a minute multiplies the render cost by that count. Single-digit ms per render keeps this comfortable; render memoization is deferred and would be revisited only if the multiplier ever bit. Second, two concurrent reads on a warm slot today both got `Arc::clone` of the same `FlaggedView`. Under the rework, both render in parallel and each allocates its own forest; the cold-slot single-flight (lock held across `build`) is preserved.

In exchange, the cache drops one rendered slot, the first mode flip no longer pays a walk, the marker write path uses one edit closure instead of two, and the undo path uses one section builder instead of two. The four-method cache API collapses to two (`get_or_build`, `rebuild`) plus the two write helpers (`apply_marker_or_build`, `rebuild_root`).

ADR-0012 stays in force. This is an extension of its principle from the scanner layer up to the cache layer: one cache, one walk, render per mode.
